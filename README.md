# event-agent

HTTP-сервис поиска анонсов событий. Другой сервис дёргает ручку `POST /runs`: агент ищет анонсы
в интернете (ddgs), извлекает события через LLM (Kimi Code) и отдаёт структурированный JSON.
Базы данных нет: между прогонами хранится маленький JSON-файл, чтобы не отдавать одни и те же
события дважды.

## Быстрый старт

```bash
uv sync
cp .env.example .env                                  # вписать OPENAI_API_KEY и OPENAI_API_BASE
uv run --env-file .env event-agent serve --port 8000  # терминал 1: сервис

curl -s -X POST localhost:8000/runs                   # терминал 2: запустить прогон → run_id
curl -s localhost:8000/runs/<run_id>                  # опрашивать, пока status == running
```

Прогон занимает 3–15 минут (поиск и LLM), поэтому ответ асинхронный. Как получить ключ и выбрать
модель, описано в [docs/configuration.md](docs/configuration.md#подключение-kimi-code).

## API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/runs` | Запускает полный прогон, `202` + `run_id`. Если прогон уже идёт, возвращает его (`already_running: true`). `409`, если состояние занято другим процессом (например, CLI-прогоном). |
| `GET` | `/runs/{run_id}` | `status`: `running` → `completed` / `partial` (сработал `run_timeout`, отдано собранное) / `failed` (см. `error`). После завершения — `events` и `stats`. `404` для неизвестного id. |
| `GET` | `/state` | Содержимое `state_path` как есть: `pages` (что читали, статусы, карантин) и `events` (все уже отданные события, ключ — `id`). До первого прогона — пустые `pages` и `events`; `503`, если файл не читается или в неизвестном формате. |
| `GET` | `/health` | Жив ли сервис и `active_run_id`. |

Результаты прогонов живут в памяти процесса и пропадают при рестарте, а события уже помечены как
отданные. Забирайте результат сразу после завершения прогона. Пример ответа, поля события и
счётчики описаны в [docs/api.md](docs/api.md).

## Запуск

```bash
uv run --env-file .env event-agent                  # HTTP-сервис (то же, что `serve`)
uv run --env-file .env event-agent serve --port 8000 [--host 0.0.0.0]
uv run --env-file .env event-agent run              # один прогон из консоли, JSON в stdout
uv run --env-file .env event-agent run --dry-run    # только список URL, без LLM и без записи
uv run --env-file .env event-agent run --general    # принудительно включить общий поиск
uv run --env-file .env event-agent --config /path/config.yaml run
```

`--config` указывается до подкоманды. Логи идут в stderr и в `logs/event-agent.log`, в конце
каждого прогона пишется итоговая строка со счётчиками. Сервис запускается одним процессом, cron
не нужен: прогон запускает вызывающий сервис.

## Docker

```bash
cp .env.example .env && cp deploy.env.example deploy.env
./scripts/deploy.sh                                 # сборка, публикация в GHCR, выкат по SSH
```

Локальный запуск в Compose, подготовка сервера, откат и резервная копия описаны в
[docs/deploy.md](docs/deploy.md). У API нет авторизации: порт нужно закрыть firewall.

## Разработка

```bash
uv run ruff check src tests && uv run ruff format --check src tests
uv run pytest -q
```

Тесты не ходят в сеть и не вызывают LLM: поиск, загрузка и модель подменяются.

## TODO

- Результаты прогонов теряются при рестарте, хотя события уже помечены как отданные: если
  вызывающий сервис не успел забрать ответ, события пропали. Вернуться, если начнутся потери или
  появится второй потребитель. Варианты: хранить результаты на диске или помечать события
  отданными только после подтверждения.
- У API нет авторизации и TLS, сейчас доступ закрыт firewall. Вернуться, если сервис понадобится
  вне внутренней сети.
- Прогон почти целиком занят поиском ddgs. Можно убрать пересекающиеся фразы между `news` и
  `text`, сократить паузу 30 с и делать её только после rate limit (ценой полноты выдачи).
- Сайты, которые рисуют содержимое на JavaScript, не читаются: известные внесены в
  `blocked_domains`, новые попадают в карантин. Вернуться, если такие источники станут важны.
- Дубли событий с разными `start_date` не склеиваются.
