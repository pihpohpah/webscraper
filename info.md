# event-agent — краткая сводка

HTTP-сервис поиска анонсов событий (FastAPI + uvicorn). SQLite удалён. Вызывающий сервис дёргает
`POST /runs`, затем опрашивает `GET /runs/{id}` и забирает структурированный список событий.
Подробности API, настройки и устройство — в `README.md`.

## Стек

Python 3.12, uv, `ddgs`, `litellm` (Kimi Code), `pydantic`, `pyyaml`, `fastapi`, `uvicorn`;
dev: `ruff`, `pytest`, `httpx`. Без async/ORM/агентных фреймворков: прогон — обычные потоки.

## Модули (`src/event_agent/`)

- `config.py` — `Config`, `load_config`, `ConfigError`.
- `deadline.py` — общий дедлайн прогона (прерываемый сон, `clamp` таймаутов).
- `search.py` — ddgs-поиск, загрузка текста (`Fetched`: ok/gone/empty/error), нормализация URL.
- `llm.py` — промпт, `Event`, вызов модели с повтором при временных сбоях, ремонт JSON.
- `state.py` — JSON-состояние: страницы (хэш, неудачи, карантин) и отданные события
  (дедупликация, new/updated/same), атомарная запись.
- `pipeline.py` — конвейер «поиск → скачивание → LLM» в общем пуле, `Budget` (лимит страниц),
  `Outcome` со счётчиками и замерами по фазам.
- `runner.py` — один активный прогон в фоновом потоке, история в памяти, `flock`.
- `schemas.py`, `api.py` — контракт и ручки; `main.py` — CLI (`serve`, `run`).

## Поток прогона

1. `prune`: убрать завершённые события и устаревшие страницы.
2. Афиши (`watch_urls`) сразу уходят в общий пул `workers`: скачать → хэш → LLM, если изменилась.
3. Параллельно идут поисковые запросы (ресурсы, затем `general_queries`); результат каждого
   запроса фильтруется (URL, блок-лист, `url_contains`, известные, карантин, лимит
   `pages_per_run`) и сразу ставится в тот же пул (скачать → LLM). Фазы не ждут друг друга.
4. Основной поток применяет результаты к состоянию (дедупликация, new/updated).
5. Сохранение состояния; `completed`, либо `partial` при `run_timeout`, либо `failed`.

## Решения, принятые при ревью

- Исправлено: потеря страниц после единичного сбоя (теперь повторы + карантин); слишком грубая
  дедупликация (учитываются город/площадка/время, защита от коротких вхождений); отсутствие
  таймаутов у LLM и дедлайна у пауз/повторов; `specs.index()` в поиске; хэш афиши считался по
  всему тексту, а в LLM уходил обрезанный; закрывающий `</page>` из текста страницы; потеря
  времени вида `19:00–21:00`; `end_date < start_date`; `event_url` с не-http схемой;
  `normalize_url` для нестандартных схем/портов; `www.` при блокировке доменов.
- Лимит событий разведён: афиша — 40, карточка — 10 (раньше 15 для всего).
- `temperature` по-прежнему не передаётся (Kimi Code), `reasoning_effort: low`.

## Оптимизация скорости (замер, одинаковый конфиг: 12 страниц в LLM, общий поиск)

Было 499 с (фазы строго по очереди, 4 воркера) → стало 266 с (конвейер, 6 воркеров, JS-домены в
блок-листе, пустые страницы в карантин сразу). После поиска страницы дожимаются за 0,1 с, то
есть **узкое место теперь — поиск ddgs** (~265 с), а не LLM. Найдено попутно: у клиента litellm
были скрытые 2 повтора (таймаут утраивался) — выключены (`max_retries=0`), повторами управляем
сами; афише дан отдельный таймаут `llm_timeout_listing` (240 с). Замеры пишутся в `stats` и лог.
Дальнейшее ускорение — только в поиске: убрать дубли запросов, сократить повтор 30 с, пауза
только после rate limit (ценой полноты).

## Известные ограничения

- JS-сайты (afisha.ru) не читаются — страница считается неудачной и уходит в карантин.
- Результаты прогонов в памяти: после рестарта `GET /runs/{id}` вернёт 404 (состояние
  дедупликации при этом сохраняется). Если вызывающий не забрал результат — события потеряны,
  так как уже помечены как отданные.
- Только один процесс сервиса; ddgs чувствителен к лимитам (`search_workers: 3`).
- `data/events.db` от старой версии не используется и может быть удалён.
