# Как устроено

Python 3.12, uv, `ddgs`, `litellm`, `pydantic`, `pyyaml`, `fastapi`, `uvicorn`. Async, ORM и
агентных фреймворков нет: прогон идёт в обычных потоках.

## Модули (`src/event_agent/`)

- `config.py` — `Config`, `load_config`, `ConfigError`.
- `deadline.py` — общий дедлайн прогона: прерываемый сон, `clamp` таймаутов.
- `search.py` — ddgs-поиск, загрузка текста (`Fetched`: ok/gone/empty/error), нормализация URL.
- `llm.py` — промпт, `Event`, вызов модели с повтором при временных сбоях, ремонт JSON.
- `state.py` — JSON-состояние: страницы (хэш, неудачи, карантин) и отданные события
  (дедупликация, new/updated/same), атомарная запись.
- `pipeline.py` — конвейер «поиск → скачивание → LLM» в общем пуле, `Budget` (лимит страниц),
  `Outcome` со счётчиками и замерами по фазам.
- `runner.py` — один активный прогон в фоновом потоке, история в памяти, `flock`.
- `schemas.py`, `api.py` — контракт и ручки; `main.py` — CLI (`serve`, `run`).

## Поток прогона

```
POST /runs → Runner (один активный прогон, фоновый поток, flock)
  → state.prune        убрать завершённые события и старые страницы
  → афиши (watch_urls) сразу уходят в пул: скачать → сравнить хэш → LLM (если изменилась)
  → поиск (ddgs)       запросы идут параллельно; каждая найденная страница сразу ставится в тот
                       же пул (скачать → LLM), не дожидаясь остальных запросов
  → сбор результатов   основной поток применяет итоги к состоянию: дедупликация, new / updated
  → сохранение state.json (атомарно, в том числе при partial)
```

Порядок источников: `watch_urls`, затем поиск по ресурсам, затем общий поиск (если
`general: true`). Результат каждого запроса фильтруется: схема URL, `blocked_domains`,
`url_contains`, уже известные страницы, карантин, лимит `pages_per_run`.

Фазы не ждут друг друга: пока идёт поиск, модель уже обрабатывает афиши и найденные ранее
страницы. Рабочие потоки состояние только читают, меняет его один основной поток. Лимит
`pages_per_run` общий: афиши резервируют места заранее, страницы из поиска берут остаток.

## Состояние

### Страницы

Страница из поиска (`article`) читается один раз. Афиша (`listing`, из `watch_urls`) грузится
каждый прогон, но если хэш не изменился (первые `page_chars` символов без учёта пробелов), LLM
не вызывается. При сбое хэш афиши не сохраняется, поэтому в следующий раз она будет перечитана.

### Неудачи и карантин

Страницы со статусом `llm_failed` и `fetch_failed` повторяются в следующих прогонах. После
`quarantine_after` неудач подряд страница уходит в карантин на `quarantine_days` дней. Страница с
пустым текстом (обычно сайт рисует содержимое на JavaScript) уходит в карантин сразу, без
повторов. Афиши в карантин не попадают и пробуются каждый прогон. `410 Gone` окончателен
(статус `gone`).

### События

Ключ — `SHA-1(название|дата|город)` плюс нечёткое сопоставление за ту же дату: `difflib` ≥ 0.85
или вхождение названия длиной не меньше 8 символов и не меньше половины длины более длинного.
Разные город, площадка или время начала дают разные события, поэтому два сеанса спектакля в один
день не склеиваются. Дубли с разными `start_date` тоже не склеиваются.

### Очистка

В начале прогона удаляются события после даты окончания и страницы старше `state_ttl_days`.

## Дедлайн

Паузы, повторы и вызовы LLM учитывают остаток `run_timeout`. Когда время выходит, прогон
завершается со статусом `partial` и отдаёт собранное. При остановке сервиса (SIGINT/SIGTERM)
активный прогон сворачивается и сохраняет состояние.

## Производительность

Узкое место — поиск ddgs. На замере (12 страниц в LLM, общий поиск) прогон занял 266 с, из них
поиск 265,9 с, а страницы после конца поиска дожимались 0,1 с. Ускорять имеет смысл только поиск.

ddgs — метапоиск и упирается в лимиты поисковиков (`RatelimitException`), поэтому
`search_workers: 3`. При лимите или таймауте запрос повторяется один раз через 30 с, затем
пропускается. Иногда выдача нерелевантна.

litellm по умолчанию делает 2 скрытых повтора и тем самым утраивает таймаут, поэтому в `llm.py`
стоит `max_retries=0`, а повторами управляет сам сервис. Афиша отдаёт до 40 событий, и вызов для
неё дольше, отсюда отдельный `llm_timeout_listing`.

Модель видит только текст страницы. Если даты в тексте нет (например, афиша в картинках),
событие не найдётся.
